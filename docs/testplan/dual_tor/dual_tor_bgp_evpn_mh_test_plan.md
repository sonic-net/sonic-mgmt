# BGP EVPN multihoming test plan

## overview
This project flattens Azure's data center network by removing Top-of-Rack (ToR) switches and directly connecting server NICs to middle-of-row dT0 switches. Each server NIC connects via max 8 independent links to 8 different dT0s, all running in active mode. BGP EVPN Multihoming (per RFC 7432 and RFC 8365) is the control-plane mechanism that provides high availability, loop-free forwarding, and fast failover across this topology. It simplifies the network topology, reduces the network latency (fewer hops from NIC to NIC), improves the network resiliency.

This test plan will primarily focus on two active-active links. It covers end-to-end verification of EVPN Multihoming correctness on SONiC switches.

## scope

**In scope:**
The scope of the test plan is to verify correct end-to-end operation of a running active-active two dT0s setup with fully functioning configuration:
* control plane verification: the correctness of the dT0s' state and the state transitions.
* EVPN Type-1 (AD-per-ES) route advertisement/withdrawal, including mass-withdrawal-driven convergence
* EVPN Type-2 (MAC/IP) advertisement for newly learned hosts and per-host ARP/ND aging.
* Data plane: the correctness of traffic flow including both upstream and downstream.

The following are out of scope for this test plan:
* the server NIC operation
* Individual component behavior(i.e. the CLI commands)
* Split horizon — not applicable in this design
* linkmgrd / mux simulator / NIC simulator — replaced by LACP
* Inter-VRF failures (T2-layer redundancy is assumed sufficient)

## testbed setup
The 2 dT0s active-active testbed setup is similar to dualtor testbed setup.
For the general SONiC testbed architecture (tiers, test servers, and neighbor simulation), see the [SONiC testbed overview](https://github.com/sonic-net/sonic-mgmt/blob/master/docs/testbed/README.testbed.Overview.md).
![Active-Active dT0s Testbed Setup](img/dualtor_bgp_evpn_mh_topology.png)
* The NIC on server will be connected to both dT0s.
    * Both dT0s are active, the server NIC will send/receive traffic via all uplinks.
    * If either of the dT0 goes standby, the server NIC will send/receive the traffic via uplink to the other dT0.
    * In dT0, all ports connecting to server live within a single /24 IPv4 VLAN and /64 IPv6 VLAN. The VLAN IP ranges will be advertised into the network by the dT0s directly.
*  For a server, if one of the dT0s goes standby (for example, the server-facing LAG goes down), it withdraws its Type-1 AD-per-ES route (mass withdrawal covering all hosts behind the ES). Until remote VTEPs process the withdrawal, traffic may be redirected over a VXLAN tunnel to the peer dT0. <br> After convergence, traffic goes directly to the remaining dT0 and no tunnel is used.
## Server NIC
The testcases defined here are under the assumptions that the server NIC is functioning correctly:
- The server NIC could send/receive traffic via uplinks to the active dT0s.

As the testing of a server NIC device operation is out of the scope of this test plan, the testcases described here needs a server NIC simulator to operate with those functional requirements listed above. In order to validate those functionalities, there should be a pretest sanity check to verify the server NIC could operates properly.


**Key topology details:**
- **2 dT0 SONiC switches** (VTEPs), each running EVPN in the same VRF with the L3VNI bound to the default VRF
- **Shared across dT0 set**: same anycast gateway IP/MAC, same eBGP ASN, same system-mac (for ESI auto-derivation)
- **LACP**: each dT0 has a Port-Channel (`PortChannel1`) toward the Server NIC; LACP PDUs exchanged per link
- **ESI**: auto-derived from system-mac + port-channel ID, or statically configured; same ESI across all dT0s for a given Server NIC
- **CE simulator**: cEOS node or PTF simulating a Server NIC with 2 port-channels (one per dT0), LACP enabled
- **T2 simulators**: cEOS nodes acting as upstream eBGP peers
- **Traffic generator**: PTF / scapy

### Testbed Assumptions
- Both dT0 VTEPs reachable to each other and to T2 via underlay (eBGP loopback peering)
- CE simulator supports LACP (active or passive mode) on both port-channels
- All EVPN control-plane daemons (`bgpd`, `neighorch`) running
- LACP slow timeout (90s) used unless stated otherwise

### Convergence & Detection Targets
| Failure class | Detection mechanism | Detection time | Expected traffic loss |
|---|---|---|---|
| Link/member failure (LAG member/PortChannel admin down) | Immediate link-down notification (no LACP timeout needed — physical/admin down is detected instantly) | < 1s | Minimal traffic loss during reconvergence |
| LACP peer timeout (server stops sending PDUs) | LACP timeout | 90s | Traffic loss bounded to ~90s detection window before failover to peer dT0 |
| Node failure (BGP kill/reboot/power loss) | BGP hold timer expiry | 90s | Traffic loss bounded to detection window; no loss after failover completes |
| Graceful shutdown (BGP NOTIFICATION) | BGP NOTIFICATION received | < 1s | No/minimal traffic loss (graceful withdrawal precedes session teardown) |
| Core isolation (uplink loss) | BGP session loss to T2 | Per BGP hold timer (90s) unless BFD is enabled | No blackholing; traffic forwarded via peer dT0 |
