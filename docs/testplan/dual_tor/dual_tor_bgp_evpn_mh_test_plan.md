# BGP EVPN multihoming test plan

## overview
This project flattens Azure's data center network by removing Top-of-Rack (ToR) switches and directly connecting server NICs to middle-of-row dT0 switches. Each server NIC connects via max 8 independent links to 8 different dT0s, all running in active mode. BGP EVPN Multihoming (per RFC 7432 and RFC 8365) is the control-plane mechanism that provides high availability, loop-free forwarding, and fast failover across this topology. It simplifies the network topology, reduces the network latency (fewer hops from NIC to NIC), improves the network resiliency.

This test plan will primarily focus on two active-active links. It covers end-to-end verification of EVPN Multihoming correctness on SONiC switches.

## scope

**In scope:**
The scope of the test plan is to verify correct end-to-end operation of a running active-active two dT0s setup with fully functioning configuration:
* control plane verification: the correctness of the dT0s' state and the state transitions.
* EVPN Type-1 (AD-per-ES) route advertisement/withdrawal, including mass-withdrawal-driven convergence
* EVPN Type-2 (MAC/IP) advertisement for newly learned hosts and per-host ARP/ND aging.
* Data plane: the correctness of traffic flow including both upstream and downstream.

The following are out of scope for this test plan:
* the server NIC operation
* Individual component behavior(i.e. the CLI commands)
* Split horizon — not applicable in this design
* linkmgrd / mux simulator / NIC simulator — replaced by LACP
* Inter-VRF failures (T2-layer redundancy is assumed sufficient)

## testbed setup
The 2 dT0s active-active testbed setup is similar to dualtor testbed setup.
For the general SONiC testbed architecture (tiers, test servers, and neighbor simulation), see the [SONiC testbed overview](https://github.com/sonic-net/sonic-mgmt/blob/master/docs/testbed/README.testbed.Overview.md).
![Active-Active dT0s Testbed Setup](img/dualtor_bgp_evpn_mh_topology.png)
* The NIC on server will be connected to both dT0s.
    * Both dT0s are active, the server NIC will send/receive traffic via all uplinks.
    * If either of the dT0 goes standby, the server NIC will send/receive the traffic via uplink to the other dT0.
    * In dT0, all ports connecting to server live within a single /24 IPv4 VLAN and /64 IPv6 VLAN. The VLAN IP ranges will be advertised into the network by the dT0s directly.
* For a server, if one of the dT0s goes standby (for example, the server-facing LAG goes down), it withdraws its Type-1 AD-per-ES route (mass withdrawal covering all hosts behind the ES). <br> T2 has only the subnet route, which 01dT0 keeps advertising, so while the link remains down T2 keeps sending 01dT0 its share of the server's traffic. 01dT0 tunnels that share to 02dT0 (VXLAN packets 01dT0→02dT0 are observed) for the whole outage, and the server receives all packets. After link recovery, 01dT0 delivers locally, with no tunnel packets and load-balancing across both dT0s.

## server NIC
The testcases defined here are under the assumptions that the server NIC is functioning correctly:
- The server NIC could send/receive traffic via uplinks to the active dT0s.

As the testing of a server NIC device operation is out of the scope of this test plan, the testcases described here needs a server NIC simulator to operate with those functional requirements listed above. In order to validate those functionalities, there should be a pretest sanity check to verify the server NIC could operates properly.


**Key topology details:**
- **2 dT0 SONiC switches** (VTEPs), each running EVPN in the same VRF with the L3VNI bound to the default VRF
- **Shared across dT0 set**: same anycast gateway IP/MAC, same eBGP ASN, same system-mac (for ESI auto-derivation)
- **LACP**: each dT0 has one Port-Channel per simulated server (`PortChannel1` for the first server; further servers use `PortChannel2` and so on, each with its own ESI). Both dT0s present the same LACP system ID, set by the PortChannel (`system_mac`).
- **ESI**: auto-derived from system-mac + port-channel ID, or statically configured; same ESI across all dT0s for a given Server NIC
- **Server NIC simulator**: PTF simulating one or more servers, each with one LAG bundling one member to each dT0, LACP enabled.
- **T2 simulators**: cEOS nodes acting as upstream eBGP peers
- **Traffic generator**: PTF / scapy

### Testbed Assumptions
- EVPN routes are exchanged between both dT0s via T2.
- Server simulator supports LACP (active or passive mode) on its single LAG, which has one member link to each dT0.
- Required processes are running: `bgpd` in the BGP container, and `orchagent` (which contains NeighOrch) and `neighsyncd` in the SWSS container.
- LACP fast rate (1 s PDUs, 3 s timeout) is configured on both dT0s and the server simulator.
- dT0s learn each other's routes only through T2, so each drops the other's routes (its own ASN is in the AS path), unless allowas-in is set (IPv4, IPv6, L2VPN EVPN) or T2 uses as-override.
- The server VLAN interface on both dT0s has static_anycast_gateway enabled, uses the same gateway_mac, and has proxy ARP/ND enabled. In addition, all server-facing PortChannels in that VLAN are configured with the platform-supported L2 port-isolation feature (same setting on both dT0s) so traffic is not bridged directly between server-facing PortChannels. Under this isolation, inter-server resolution/forwarding in the SS scenarios is expected to occur via the anycast gateway path (routed), not direct L2 bridging.
- Pretest sanity check (before SS cases):
    * From Server-0, resolve Server-1 IP and confirm anycast gateway MAC is used (not Server-1 MAC).
    * On Server-1 link capture, confirm no direct ARP/NS or unicast frames from Server-0 are bridged.
    * Verify Server-0 -> Server-1 probe is routed (TTL/Hop-Limit decrement observed).
    * If any check fails, mark SS prerequisite failed and do not run SS functional checks.
- BGP graceful restart (GR) is disabled on all sessions; BFD is not used.

**BGP peering:** each dT0 runs eBGP sessions to the T2 simulators carrying the IPv4 unicast, IPv6 unicast and L2VPN EVPN address families. T2 propagates the EVPN routes between the two dT0s. The VXLAN tunnel is between the two dT0 VTEPs.


### Convergence & Detection Targets
**Target release and failover model:** this plan covers the release **without UAP** (the upcoming feature where a dT0 stops attracting traffic for the servers behind its failed link) and without hardware fast reroute. T2 has only the subnet route, so it keeps sending 01dT0 its share of a server's traffic after 01dT0 loses its link; withdrawing the Type-1 does not change that. 01dT0 tunnels that share to 02dT0 until the link recovers. The dT0 that lost its link moves traffic in software (tens to hundreds of ms).
**Pass/fail loss criteria:**
* For a single link failure, measure loss from fault injection through detection and forwarding convergence, using the failure-specific loss budgets in the table below (including the LACP timeout where applicable).
* Two or more link failures on the path lose traffic until the network converges (see DS-16, US-13, SS-13).
* For multiple link failures with a surviving end-to-end path, traffic resumes after convergence. If all server links fail (DS-16, US-13, SS-13), delivery remains unavailable until at least one link is restored; verify the specified drop/no-loop behavior during the outage.
* Timers (LACP fast rate with 1 s PDUs and a 3 s timeout, BGP hold time) are taken from the testbed configuration.

| Failure class | Detection mechanism | Detection time | Expected traffic loss |
|---|---|---|---|
| Link/member failure (LAG member/PortChannel admin down) | Immediate link-down notification (no LACP timeout needed — physical/admin down is detected instantly) | < 1s | ≤ 500 ms |
| LACP peer timeout (server stops sending PDUs) | LACP timeout | ~3s | 3.5 s (3 s detection + 500 ms) |
| Node reboot / power loss on 01dT0 | Loss of carrier on 01dT0's links (NIC drops its members, T2 stops forwarding over dead links at once) | Links: immediate; | ≤ 500 ms; traffic does not wait for the hold timer |
| BGP process kill on 01dT0 | TCP session close seen by peers immediately (GR disabled, so routes are withdrawn) | Immediate | ≤ 500 ms |
| Graceful shutdown (BGP NOTIFICATION) | BGP NOTIFICATION received | < 1 s | ≤ 500 ms |
| Core isolation: uplinks shut down | Link-down on the uplinks (immediate) | < 1 s | ≤ 500 ms; 01dT0 takes its server links out of service and the server stops using its member to 01dT0 |
| Frozen bgpd (SIGSTOP) or T2 session left up after node loss | BGP hold timer (90 s by default) | Hold timer | T2 keep the routes until expiry (and keeps advertising them to 02dT0); traffic does not wait for it |

## testcases
These testcases are to verify the traffic flow behaviors as expected following the configuration changes or dT0 state changes.
For all testcases in the packet flow scenario:
* Both dT0s are active initially.
* For cases that require the surviving dT0 to retain host state after the failed dT0 withdraws its Type-2, first learn each affected host locally on the surviving dT0 and verify that it is not relying solely on a synced copy. Baseline sync-only cases are exempt from this precondition.
**Neighbor-removal procedure (used by the cases that say "neighbor removal"):**
1. With the PortChannel down on 01dT0, wait past the aging time (set `base_reachable_time_ms` short; the SONiC default is 30 minutes). Expiry alone is not treated as removal.
2. Delete the host's neighbor entry on 01dT0 explicitly (for example `ip neigh del <ip> dev <vlan>`), so removal is deterministic and distinct from natural aging.
3. Poll until both hold, within the removal timeout configured for the testbed: (a) `show arp` / `show ndp` on 01dT0 has no entry for the host, and (b) `show bgp l2vpn evpn route type macip` on 02dT0 has no Type-2 from 01dT0 for the host. If either is not met within the timeout, the case fails.
4. Only after step 3 passes, run the Phase 2 checks and then restore the PortChannel (recovery cases). For DS-13, step 3 must hold for all N hosts.
